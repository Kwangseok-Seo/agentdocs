# M9 — The editor, and a screen that follows the disk

> Roadmap: M9

## What was done

`e` hands the selected file to an editor, and the screen comes back when the editor ends, with whatever it wrote. The editor is the one `$VISUAL` names, or else `$EDITOR`, or else notepad on Windows and vi elsewhere; it runs in the same terminal or in a window of its own, and the screen waits for it either way. A Bundle hands over its Lead; a directory, or something that could not be read, has nothing to hand over. An editor that ends badly says so at the right end of the bottom row, in red, for two seconds:

```
$ cd my-project && agentdocs      # a 120 x 30 console, read back cell by cell; EDITOR=agentdocs-no-such-editor
┌Sources───────────────────┐┌Entries───────────────────────┐┌Preview───────────────────────────────────────────────────┐
│GLOBAL                    ││  changelog                   ││# Guide                                                   │
│  skills:6                ││  guide                       ││                                                          │
…
└──────────────────────────┘└──────────────────────────────┘└──────────────────────────────────────────────────────────┘
 j/k ↓/↑ move   l/h open/close   tab pane   e edit   drag copy   q quit                            editor: exit code: 1
```

## Pitfalls actually hit

Each is written up where the concept lives:

- [[processes]]: three layers taken for two — *outer* and *inner* had been the explanation's words for `.status()`'s two, and `edit()` wraps a third round them. Settled in slice 1.
- [[result-and-errors]]: which layer an `Err` comes back in, when what `?` does was known exactly. Settled in slice 1.
- [[closures]]: calling and handing over — back in slice 1 as `chosen(env::var_os())`, and settled in slice 2, `read_input(event::read, …)` picked at the first attempt. And, **not settled**, that an argument is worked out before the call whether or not the call uses it.
- [[event-loop]]: **not settled** — a frame taken to be sent whole. It is how ratatui works, not Rust, and had not been taught in the session before it was asked.
- [[channels]]: one `Sender` moved into two places. Settled in slice 2.
- [[threads]]: a thread taken to be where its work is, rather than where its code has got to. Settled in slice 2.

The assistant's words steered answers twice. In slice 1 the explanation named `.status()`'s layers *outer* and *inner*, and the answer about `edit()`'s three put those words on the wrong pair; layers are numbered from the start now. In slice 2 the explanation covered `move` and `clone` one at a time and never the two together, and the answer to *how does the second thread get a `Sender`* moved the only one.

What worked was finding the reason before explaining again. After slice 1's first round of review questions went 0 for 3, the author chose diagnosis over a line-by-line explanation, and four diagnostic questions found two different things: `?` was understood exactly, and the gap was which of two layers its error lands in; and `env::var_os()` was being read as the way documentation writes that something is a function. In slice 2 the question of where a thread is was answered by a log of the two threads taken while the real screen ran, and two review questions about other moments were both right.

## What measurement changed

**How `$EDITOR` is run.** Three ways were built and run before the author chose, with a stand-in editor that logs what it is handed, as an `.exe` and as a `.cmd`: splitting the value and starting the first word (how herdr starts one on Windows), the shell with the path on its line, and the shell with the path in a variable. Splitting found no `code` and no `code --wait` — `Command` adds only `.exe` to a name — and the path on cmd's line handed a file named `100%PATH%.md` to the editor with the machine's `PATH` inside its name, exit 0. The path in a variable came through 24 of 24: four ways of naming an editor against six file names holding `%`, `!`, `^`, `&`, `$` and a space. Through Git's `sh`, the Unix form came through 5 of 6; the sixth, `quote'x.md`, had lost its quote before `sh` was given it — in how Git's tools pass arguments on Windows, not in the form. cmd's `/s` switch was tried and changed nothing, since the line always holds four quotes or more; it was left out. The author chose the shell with the path out of the line ([ADR-0010](../../adr/0010-the-editor-runs-through-the-shell.md)).

**What opens when nothing names an editor.** Neither variable is set on this machine. herdr opens notepad on Windows and vi elsewhere; the Store's notepad, 11.2607, was measured to keep `.status()` waiting until its window closed — even when the file opened as a tab in a window already open. Closing only the tab was not measured.

**How to hear a change.** Walking every Source again once a second and comparing was timed first. One pass cost 21 ms of processor time with this repository as the project — 100 files and 834 KB of text, as it was then — which is 2.1% of one core, and 37 ms with cli-printing-press's 314 files and 5.1 MB, 3.7%; it grows with what there is to read, and a change could wait a second to show. notify was then run against a tree like the Sources:

| what happened | what notify reported (Windows) |
|---|---|
| nothing, for 2 seconds after the watches began | 1 report, the `docs` directory modified — not explained |
| a file written where it was | 2 reports, the first after 1–2 ms |
| a file written aside and renamed over the old | 8 |
| a file behind a link, below a directory watched whole | 0, whichever path it was written through |
| the same, with the link's own path watched | 2 |
| a directory that was not there, watched | an error: not a file nor a directory |
| the same directory appearing, its parent watched | 1 |
| two builds of a project whose `target/` is under the root, the root watched alone | nothing in 30 seconds |

The author chose notify ([ADR-0011](../../adr/0011-changes-are-heard-not-polled.md)). Comparing two Walks of everything here took 26 µs, so a report that changed nothing costs a Walk and nothing else.

**What notify does elsewhere.** Read in notify 8.2's source, not run, since no Linux machine was at hand: below a directory it watches whole, it follows links unless told not to; and on Linux it asks for every file opened, and reports each. The Walks open every file they read, so on Linux every reading would have been heard as a change, and set off the next. Both are turned off: `with_follow_symlinks(false)`, and reports of a file opened, read or closed are not passed on.

**Whether a thread reading the terminal takes an editor's keys.** First a small program: a thread reading the console while a child program read it too, "hello" typed in 20 times. The child got it whole 6 times; with the thread waiting to be told, 20. Then the real loop, driven in this console with a stand-in editor that records what it gets: written as it is, 20 of 20; with the thread never waiting, 5 of 20, and in 7 the thread took the `e` of `hello`, the loop opened the editor again, and the `q` typed after went to that editor, so the screen never ended.

**How the loop is woken.** A change is on screen 118 to 128 ms after it is written, over ten runs of the release build in this console — 100 ms of it on purpose, so that the eight reports of one save are read once.

## Decisions

Two records were written. [ADR-0010](../../adr/0010-the-editor-runs-through-the-shell.md): how `$EDITOR` is run is what a user's setting means, so changing it later breaks settings that work now; nobody would guess from the code why cmd is given its line in pieces with the path in a variable; and the alternative that names a missing editor exactly was given up for it. [ADR-0011](../../adr/0011-changes-are-heard-not-polled.md): a dependency, a thread and a channel are not taken back lightly; walking everything on a timer is the obvious way, and simpler; and what was given up — no dependency, and a watcher that cannot disagree with the Walks — was real.

- **Chosen by the author**: the shell, with the path out of its line; notepad or vi when nothing names an editor, as herdr does; notify over walking everything every second; the terminal checks for M9 done once, at its end.
- **Chosen by the assistant and reported**: `e` acts on the selected row from any pane, and on a row with no file does nothing; every Source is read again after the editor, since a linked Bundle shows one file in two Sources; the notice takes the place "copied to clipboard" takes, in red; the key hints gain `e edit` and lose `click select`; the terminal read on a thread that waits to be told to go on; the Sources read again 100 ms after the first report, not put off by the next; what a Walk finds taken only where it differs; the selected row kept by its path; what to watch worked out beside the Walks; a watch that cannot be made tried again each time round the loop; one watch to a path, below winning over alone; a watcher that cannot be made at all ends the screen with the error.

The existing records were checked against what M9 added. [ADR-0001](../../adr/0001-read-only-viewer.md) is M9's own subject, and holds as written: nothing is edited in place, and the Sources are read again when the editor ends. [ADR-0007](../../adr/0007-links-are-listed-not-followed.md) gained a surface, watching. A link watched by its own path is not walked into — nothing behind it is listed — but notify, left to itself, would have watched below every link under a directory watched whole, on Linux and the BSDs; that is what the check found, and it is turned off. [ADR-0008](../../adr/0008-screen-for-a-bare-command-at-a-terminal.md): the listing is untouched, below. The others govern discovery and walking, which M9 reads but did not change. `CONTEXT.md` gained no word: an editor, a watch and a thread belong to the screen, not to the domain.
