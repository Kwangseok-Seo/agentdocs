# Changes on disk are heard from the system, and what to watch follows each Walk

The screen hears that a file changed from the system's own notifications, through the `notify` crate, and reads every Source again shortly after the first word of a change (`SETTLE`), keeping what a Walk finds only where it differs from what the screen already has; what to watch is worked out beside the Walks, by `Source::watched`, from each Source's Walk and from what that Walk found — because walking every Source again on a timer reads every file each time, at a cost that grows with the documentation it reads, while with notifications nothing is read until something changes; the cost accepted is a dependency whose backends differ from one platform to the next, and a second statement of how far each Walk reads, which has to be kept beside the first.

**What is watched.** A Source's directory alone, for a Walk that reads one level, and everything below it, for one that descends. A link standing in for a Bundle is watched by its own path as well: the Walk reads the Bundle's Lead through it, and a change behind a link is not reported to a watch on the directory holding the link. A directory that is not there cannot be watched, so the nearest directory above it is, which hears it appear. A link to a single file, which a Walk also reads through, is not watched; a change behind one shows once anything else changes.

**What notify does by default is not ours.** Below a directory watched whole, notify follows links on Linux and the BSDs unless told not to; a link is never walked into ([ADR-0007](0007-links-are-listed-not-followed.md)), so it is not watched into either. And notify reports a file being opened or closed — on Linux, every open, which the Walks' own would set off, so that taking those reports for changes would have the screen read its Sources again for ever. A report of that kind is not a change. Both of these were read in notify 8.2's source; neither was run, since only Windows was at hand.

**Rejected: walking every Source again once a second and comparing.** It needs no dependency and cannot disagree with the screen, since the Walk is the only statement of what is read. Measured on this machine's documentation before the choice, every pass cost processor time where notify reads nothing until a report comes, more of it the more there is to read, and a change could wait up to a second to show; the numbers are in the [M9 log](../learn/milestones/M9.md).

**A consequence: the terminal is read on a thread of its own.** The loop now waits for two things — the terminal and a change — and waits for both on one channel. The thread reading the terminal reads one event and then waits for the loop to say go on, which the loop says once it is done with that event, an editor run from it included: a thread that read all the while an editor had the terminal took the editor's keys.
