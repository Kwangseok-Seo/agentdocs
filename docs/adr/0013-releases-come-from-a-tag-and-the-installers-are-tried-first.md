# Releases come from a tag, one archive per target, and the install scripts are tried on them first

A tag `v<version>` — which must be the version `Cargo.toml` says, and the version each binary says when run — builds the program for five targets on GitHub's runners and publishes it as a GitHub release: one archive per target named `agentdocs-<target>.tar.gz`, or `.zip` for Windows, holding the binary, the README and both licences, with `SHA256SUMS` and the two install scripts beside them; and nothing is published until `install.sh` and `install.ps1` have installed those very files on Linux, macOS and Windows. The cost accepted is that the archive names and the `releases/latest/download/` addresses are a contract from the first release on — the install scripts, and anyone's own, fetch by them — and that the scripts' first run against GitHub's own addresses is the first public release, since a private repository's releases cannot be fetched without signing in.

**The install scripts are assets of the release they install**, not files read from `main`: `releases/latest/download/install.sh` is the script that came with the archives it expects, so a change to how archives are named or packed cannot meet a script that predates it. Each checks the archive against `SHA256SUMS` before anything is installed, and installs to the user's own directories, `~/.local/bin` and `%LOCALAPPDATA%\Programs\agentdocs\bin`, without asking for an administrator.

**Linux gets one static binary per architecture**, linked against musl rather than the distribution's glibc, so that the same file runs on every distribution — Alpine, which has no glibc, included. **The Windows binary carries its C runtime** rather than loading `vcruntime140.dll`, which a Windows without the Visual C++ redistributable does not have.

**Not now: crates.io, package managers, a manifest of our own.** Publishing a crate cannot be taken back, and it builds from source, which needs Rust — `cargo install --git` already serves whoever has Rust. Homebrew, Scoop and winget are each a repository of their own to keep up, and can be added beside this later without changing it. herdr publishes a `latest.json` from its website for its installer and its own updater; there is no website here, and GitHub's `latest` address does the same for an installer.
